# Zurich Safe Cycling Route Recommender

A Python-based safe cycling route recommender for Zurich, developed for the *Computer Programming & Data Science* course at ETH Zürich (June 2026).

---

## Overview

Standard route planners optimise for distance or travel time, ignoring cycling safety. This project builds a full pipeline that:

1. **Step 1 — Data & Safety Scores** Processes police-registered bicycle accident data from Stadt Zürich Open Data and converts it into hourly, edge-level safety scores on the Zurich cycling network.
2. **Step 2 — Routing** Computes four route strategies (shortest, fastest, safest, balanced) using a weighted shortest-path algorithm on the OpenStreetMap cycling network.
3. **Step 3 — Visualisation** Presents routes and a summary dashboard interactively through a Streamlit web application.

## Step 1 — Data Cleansing & Safety Scores

The original Step 1 accident-processing workflow has been extended with hierarchical Bayesian partial pooling. The current implementation is:

```bash
python scripts/update_bayesian_risk.py
```

Run from the repository root. The existing accident source, 50 m spatial association, hourly score interface and road-type penalties are retained; the fixed hourly smoothing is replaced by Bayesian estimation.

### What it does

- Loads `data/raw/roadtrafficaccidentlocations.csv` (police-registered accident records from Stadt Zürich Open Data, 2011–2025)
- Filters to bicycle/e-bike accidents with valid coordinates and hours — 8,753 records retained from 70,767
- Uses the cached Zurich cycling network from OpenStreetMap via OSMnx and projects both datasets to Swiss LV95 (EPSG:2056)
- Assigns accidents to road edges within a 50 m buffer and computes accident density (accidents per km of edge)
- Replaces the original fixed hourly smoothing with a city / road-class / segment hierarchical Gamma-Poisson model. Sparse segment estimates partially pool toward their road-class mean; city and road-class means have sampled posterior distributions.
- Outputs posterior accident-intensity means, standard deviations and 95% credible intervals. Identical reverse-direction geometries are consolidated for estimation, then scores are mapped back to directed edges.

See [hierarchical Bayesian model details](docs/hierarchical_bayesian_risk.md) for equations, priors and diagnostics. The model uses length-years as a spatial exposure proxy, not cyclist traffic volume.

- Normalises to a 0–1 risk value and adds an OSM road-type penalty:

| Road type   | Penalty |
|-------------|---------|
| Cycleway    | 0.00    |
| Residential | 0.15    |
| Tertiary    | 0.30    |
| Secondary   | 0.45    |
| Primary     | 0.65    |

- Computes a final percentile-ranked `risk_score` per edge and hour (0 = safer, 1 = riskier); `safety_score = 1 - risk_score`

### Output

```
data/processed/zurich_hourly_edge_safety_score.csv
```

Columns: `u`, `v`, `key`, `edge_id`, `time_period` (`h00`–`h23`), `safety_score` / `risk_score`.

If only `safety_score` is present, Step 2 automatically derives `risk_score = 1 − safety_score`, and vice versa.

## Step 2 — Routing

### What it does

Loads the Zurich cycling graph and the hourly safety scores from Step 1, then computes four route strategies for a given origin, destination, and departure hour using NetworkX shortest-path search:

| Strategy            | Edge weight minimised              | Interpretation                         |
|---------------------|------------------------------------|----------------------------------------|
| `shortest_distance` | Length (m)                         | Shortest physical distance             |
| `fastest_time`      | Travel time (s)                    | Shortest estimated cycling time        |
| `safest_route`      | Risk cost = risk\_score × length   | Lowest distance-weighted risk exposure |
| `balanced_route`    | 0.5 × t_norm + 0.5 × risk_norm    | Trade-off between time and safety      |

**Fixed destinations:** ETH Zentrum · ETH Hönggerberg

### Run Step 2

```bash
# Default run (Wiedikon origin, hour 8, both campuses)
python scripts/run_step2_pipeline.py

# Custom origin, destination, and hour
python scripts/run_step2_pipeline.py \
  --origin-lat 47.37139 \
  --origin-lon 8.51680 \
  --origin-name "Custom start" \
  --destination both_campuses \
  --time-period 17
```

The `--time-period` argument accepts `8`, `08`, `h08`, `hour_08`, or `08:00` interchangeably.

### Outputs

| File | Description |
|------|-------------|
| `results/step2_current_routes.geojson` | One feature per road link per route. Properties: `route_type`, `risk_score`, `length_m`, `travel_time_s` |
| `results/step2_route_summary.csv` | One row per route. Columns: `route_type`, `estimated_travel_time_min`, `mean_risk_score`, `total_distance_km`, `total_risk_exposure` |
| `results/step2_route_summary.md` | Human-readable summary table |
| `results/step2_current_route_plot.png` | Static matplotlib overview plot |

> The GeoJSON represents the **current query only** — not a precomputed database of all routes. Step 3 reads it fresh after each user query. Each feature is one road link/edge, allowing the frontend to colour individual segments by local risk.

### Benchmark and weight sensitivity

The existing four-strategy routing model is evaluated on all covered intersection origins with directed paths to either ETH campus: **27,598 OD pairs** at **08:00**, with equal weight per OD. This is a model-network population, not observed traffic demand; no extra municipal-boundary clipping or physical-junction consolidation is applied.

```bash
python scripts/benchmark_all_campus_od.py
python scripts/weight_sensitivity.py
```

The benchmark computes 110,392 routes. Sensitivity analysis evaluates 11 time weights (0, 0.1, ..., 1), with risk weight equal to 1 minus the time weight, on the same OD population. The selected final balanced weights are **time 0.8 / risk 0.2**; distance remains an evaluation metric.

| Strategy | Mean model risk exposure reduction | Mean time increase | Mean distance change | Mean extra time |
|---|---:|---:|---:|---:|
| Shortest | 19.66% | 7.34% | -3.54% | 1.42 min |
| Balanced (0.8 / 0.2) | 41.71% | 18.24% | +2.47% | 3.50 min |
| Safest | 52.67% | 94.85% | +52.72% | 19.01 min |

All changes are relative to the raw fastest route, computed separately per OD and then averaged. Modeled exposure is the sum of risk_score times edge length; these reductions are not observed accident-probability reductions. The existing edge min-max normalization can make pure normalized endpoints differ from raw fastest/safest routes.

[Evaluation methods](docs/benchmark_and_sensitivity.md) | [Final benchmark](results/benchmark_all_campus_od/report.md) | [Sensitivity report](results/weight_sensitivity/report.md)

## Step 3 — Visualisation & Interaction

### What it does

A Streamlit web application (`frontend.py`) that:

- Lets the user click an interactive map in the sidebar to set their cycling origin
- Selects destination and departure hour via dropdowns
- Calls `backend.py` to run the Step 2 routing pipeline
- Renders all four routes on a dark CartoDB basemap, coloured by local risk score (green → yellow → red, 0.0–1.0)
- Displays a **Route Summary Dashboard** with KPI cards (best time, lowest risk, shortest distance) and bar charts comparing all visible routes

### Run locally

```bash
streamlit run frontend.py
```

## Deployment

The Streamlit application can be deployed directly from this repository using Streamlit Cloud, with `frontend.py` specified as the entry point.

For CARTO Dark Matter, set `CARTO_BASEMAP_API_KEY` in `.streamlit/secrets.toml` locally or application Secrets on Streamlit Cloud; `.streamlit/secrets.toml.example` provides the template. Both maps fall back to OpenStreetMap when no key is configured. Real secrets and the generated HTML map are ignored by Git.

The processed risk CSV uses Git LFS. Fetch it with `git lfs pull`; reproducible large intermediate files are excluded from Git. See [GitHub packaging](docs/github_upload.md).

## Limitations

- Risk scores, including the Bayesian extension, are derived from historical police-registered accident records and therefore represent long-term risk patterns rather than real-time cycling conditions.
- Accident reports capture only recorded incidents and may underrepresent minor crashes or near-miss events, potentially introducing reporting bias.
- Safety estimation is based primarily on accident density and road classification, and does not explicitly account for factors such as traffic volume, weather, lighting conditions, road surface quality, or cyclist experience.

---

- Bayesian mixing diagnostics do not establish predictive accuracy; held-out temporal validation has not yet been performed.
